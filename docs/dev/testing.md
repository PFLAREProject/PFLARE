# Test system (agent reference)

How tests are wired
- Test executables are listed by hand in `TEST_TARGETS` (top `Makefile`, ~line 190); `adv_1dk` is appended only when PETSc has Kokkos. `CHECK_TARGETS` (`adv_diff_fd matrandom`) is what `make check` runs.
- The Fortran test drivers (`tests/*.F90`, listed again in `FORTRAN_TEST_TARGETS`) are only built when PETSc has its Fortran bindings (`PETSC_USE_FORTRAN_BINDINGS`, read from `petscconf.h` by the top `Makefile`, which also gates the Fortran interface in `src/fortran`); otherwise they are filtered out of `TEST_TARGETS` and `CHECK_TARGETS`.
- `tests/Makefile` has no per-test declarations: it is a set of `run_tests_*` recipe targets whose bodies are literal `./exe -options` lines with `@echo` labels. Groups: `run_tests_load_{serial,parallel}`, `run_tests_no_load_short_{serial,parallel}`, `run_tests_no_load_{serial,parallel}`, `run_tests_medium_{serial,parallel}`, `run_tests_copies`, `run_check`.
- `run_tests_copies` (`make tests_copies`, serial and parallel in one group) runs the `-check_copies` drivers that fail on any host/device copy in a second solve. Not part of `make tests` or the default `tests_search` groups: it only means anything on a GPU and its parallel lines need GPU-aware MPI, so only the GPU CI workflow calls it.
- Executables are built by PETSc's implicit rules; `tests/Makefile` itself exports `LD_LIBRARY_PATH`/`DYLD_FALLBACK_LIBRARY_PATH` pointing at `lib/`.

Checklist for adding a test
1. Add the driver source in `tests/`.
2. Add the executable name to `TEST_TARGETS` in the top `Makefile` (a Fortran driver also to `FORTRAN_TEST_TARGETS`).
3. Add the executable name to `.gitignore` (there is a marked section for compiled test executables).
4. Add invocation line(s) to the appropriate `run_tests_*` group(s) in `tests/Makefile` — usually both a serial and a parallel (`mpiexec -n 2`+) variant, with an `@echo` label describing the test. Prefix every line that runs a Fortran driver with `$(SKIP_FORTRAN)`.

TEST_MATCH mechanics (`make tests_search TEST_MATCH="<substring>"`)
- Dry-runs (`make -n`) the groups in `FILTER_RUN_TARGETS` (default = all groups; load groups dropped when 64-bit indices or single precision), joins continuation lines, greps command lines for the substring with `grep -F`, and evals each matching `./exe` line.
- Empty `TEST_MATCH` is an error (exit 2); zero matches is a success ("No matching test commands found").
- Override the searched groups with `FILTER_RUN_TARGETS="run_tests_no_load_serial ..."`.

Precision / index-size gates
- Load tests (which read binary matrices from `tests/data/`) only run on 32-bit indices + double precision (`RUN_LOAD_TESTS` in the top `Makefile`) — the data files are written in that format.
- `KSP_RTOL` is precision-aware: 1e-5 single, 1e-10 double (`tests/Makefile`).
- Fortran gate: every recipe line that runs a Fortran driver starts with `$(SKIP_FORTRAN)` (`tests/Makefile`), including the `for` loop lines over `ex12f_gmres_poly`. Without Fortran bindings it expands to `@echo "  [skipped without Fortran bindings]"; exit 0;`, so the line prints that and exits its shell before the command (an echo of the command, as `SKIP_SINGLE` does, cannot swallow a `for` loop); with them it is empty. `run_check` prints "Fortran check skipped (PETSc configured without Fortran bindings)" in place of its `matrandom` check, like the MPIUNI case. `tests_search` evaluates each command in a subshell so the `exit` only ends that command. Put `$(SKIP_FORTRAN)` before any `$(SKIP_SINGLE)` on the same line.
- Individual commands that fail under single precision are prefixed with `$(SKIP_SINGLE)`, which turns them into echoes in single builds. See the comment at `tests/Makefile:36-47` for the recurring reasons (power/Arnoldi polynomial-basis overflow; `-pc_air_reuse_sparsity` pattern staleness). Gate only the specific failing command only if absolutely necessary when the failure is understood, never a whole class.

Python tests
- `make tests_python` (also included in `make tests`). Requires petsc4py and `PYTHONPATH` containing `python/`.

Golden logs (`make tests_golden`)
- Records what the suite computes, not just whether it passes, so a change that should not alter results (e.g. the staged port of the Fortran core, `docs/dev/fortran_removal_plan.md`) can be checked command by command.
- `tools/capture_test_logs.sh` enumerates the commands exactly as `tests_search` does (dry run of the `run_tests_*` groups plus `run_check`, same `RUN_LOAD_TESTS`/`SKIP_SINGLE`/`SKIP_KOKKOS`/`SKIP_FORTRAN`/MPIUNI gates), runs each with `-ksp_converged_reason -ksp_monitor` appended to `PETSC_OPTIONS`, and keeps one log per command plus `meta.txt` (configuration) and `commands.tsv`. SKIP_* commands are recorded as skipped.
- `tools/compare_test_logs.py` reduces each log to a record: exit status, converged reasons with iteration counts, residual histories, and the `-pc_air_print_stats_timings` block via `tools/parse_pflare_output.py` (levels, rows, F/C points, complexities; timings are dropped). `summarize` writes the records as compact JSON; `compare BASE NEW` takes capture directories or JSON files.
- Rule: exit status, converged reasons and iteration counts identical; residual norms to a relative tolerance (1e-8 double, 1e-4 single; `--res-rtol`, `--res-atol`); stats integer fields identical; complexities to 1e-10 (`--complexity-rtol`). Every baseline command must still exist (`--allow-missing` to relax) and every new command must pass. Exits 1 and prints each difference otherwise.
- Interleaved ranks: a command on several MPI ranks whose KSPs live on sub-communicators prints monitors from every rank in an order that changes run to run (today only the parallel `comm_self_then_world` lines, which solve on `PETSC_COMM_SELF`). When the solves of such a command match only after sorting (residual norms and converged reasons), the comparison reports it as `REORDERED` and passes; `--strict-order` makes it a failure.
- Known run-to-run variation: on 4 ranks the residuals of the 3+ level hierarchies change in the last digits from run to run in the non-Kokkos images (seen in `run_tests_no_load_parallel` `mpiexec -n 4 ./adv_diff_fd ... -pc_air_cf_splitting_type agg ...`, relative differences up to about 4e-9 at the last iterations; never on 2 ranks, not in the Kokkos image). It already happens at the base commit, so it is not a PFLARE change; it is consistent with PETSc summing off-rank contributions in message arrival order once three or more ranks contribute to the same row. It is inside the 1e-8 tolerance, so `--res-rtol 0` is not usable for bitwise checks of that command.
- A capture of a build without Fortran bindings (config name suffix `_no_fortran`) records the `SKIP_FORTRAN` lines as skipped, under their `echo ...; exit 0; ./<driver> ...` command text. Compared against a Fortran-enabled capture of the same commit, each Fortran command is MISSING from it and appears as NEW (skipped), so pass `--allow-missing` and check that the missing ones are exactly the Fortran drivers; every other command must compare as usual.
- `make tests_golden_capture` writes a capture to `GOLDEN_DIR` (default `tests/golden_logs/`, gitignored). `make tests_golden` captures and compares against a baseline JSON you produced earlier with `compare_test_logs.py summarize` (looked up as `$(GOLDEN_BASELINE_DIR)/<config>.json`, default `tests/golden/`, not committed), where `<config>` follows the CI job names (`gnu_debug`, `gnu_opt`, `gnu_opt_kokkos`, ...; override with `GOLDEN_CONFIG`). `GOLDEN_JOBS=N` runs N commands at once (results do not depend on it).
- To compare two trees directly (e.g. a base commit against a branch, both built in the same image): `tools/capture_test_logs.sh -r <base tree> <dir A>`, `tools/capture_test_logs.sh <dir B>`, then `tools/compare_test_logs.py compare <dir A> <dir B>`. The `gnu_opt_golden_logs` CI job does exactly this for the merge-base of a PR and its head, so PETSc `main` moving under the images never shows up as a difference, and uploads the head capture as an artifact.
- No baselines are committed (they would drift whenever the images pick up a new PETSc `main`). To check a change, capture the base tree and the changed tree in the same image and compare them, as above. Accepting results that PFLARE changed is not allowed without a documented reason: any difference is a failure until explained. (The random-generator stage of the Fortran removal plan, stage 9, was the one stage allowed to re-baseline; it did not need to, as its C generator reproduces gfortran's bitwise, and that exception has now passed.)
